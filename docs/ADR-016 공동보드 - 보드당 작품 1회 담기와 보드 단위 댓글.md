> **ADR-016 · Domain · Accepted · 2026-08-09 (2026-08-13 결정 번복)**
> 친구들과 졸업스냅 후보를 모으는 공동보드를 어떻게 모델링할지 결정. → **같은 작품은 보드에 한 번만 담긴다(먼저 담은 사람이 임자). 댓글은 작품이 아니라 보드에 단다. 방장 개념을 두되 초대는 멤버 누구나 할 수 있다.**
>
> ⚠️ 최초 결정은 "참여자마다 한 행 + 조회에서 중복 제거" 였으나 **뒤집혔다.** 경위는 아래 [[#결정 번복 (2026-08-13)]] 참고.

## 맥락
- 고객이 친구들과 함께 후보 작품을 모으고 의견을 나누는 기능. 공동보드는 **고객 전용**(`owner` 가 `Customer`)이다.
- 화면은 작품 카드 그리드 + 하트(좋아요) + 멤버 칩 + 댓글. **카드는 작품 하나당 하나**로 보인다.
- 초기 스캐폴딩은 `PickBoard`/`PickCandidate`/`BoardParticipant` 였고 선정 상태(`SelectedStatus`)·변경 이력(`PickBoardHistory`)까지 있었다. 실제 기획에는 없는 개념이었다.

## 결정
- **네이밍을 `Shared*` 로 통일** — `SharedBoard` / `SharedMember` / `SharedArtwork` / `SharedArtworkLike` / `SharedComment`. 기획 용어(공동보드·공유멤버·공유작품)와 1:1로 맞춘다.
- **선정 상태·변경 이력 제거** — 기획에 없는 개념이라 스캐폴딩만 남아 있었다. 필요해지면 그때 추가.
- **`SharedArtwork` 는 보드당 작품 하나에 한 행** — unique `(shared_board_id, artwork_id)`.
    - `customer` 는 **그 작품을 담은 사람(소유자)** 이고, 뺄 수 있는 것도 그 사람뿐이다.
    - 다른 참여자가 이미 담은 작품을 담으려 하면 **409**(`SHARED_ARTWORK_ALREADY_SHARED`). 프론트가 저장 목록 조회의 `sharedBy` 로 미리 막지만, 동시에 담는 경우가 있어 서버에서도 검증하고 DB unique 가 최종 방어선이다.
    - 조회는 **담긴 그대로** 내려간다. 중복 제거가 필요 없다.
- **`SharedComment` 는 보드 단위** — 개별 작품이 아니라 보드에 단다. 후보 전체를 놓고 나누는 대화라서.
- **`SharedMember` 는 방장도 포함** — 보드 생성 시 방장이 참여자 행으로 함께 들어간다. 멤버 목록·인원수에 별도 분기가 없어진다.
- **방장 권한은 보드 이름 수정·삭제뿐.** 초대는 멤버 누구나 할 수 있다([[ADR-017 공동보드 초대 링크 - PK 대신 초대 코드]]).
- **방장은 보드를 나갈 수 없다**(`SHARED_BOARD_OWNER_CANNOT_LEAVE`). 삭제만 가능. 단 **회원 탈퇴 시에는 위임**한다([[ADR-010 회원 탈퇴·역할 해지 - soft delete·익명화·문의 자동취소]] 갱신분).
- **멤버 탈퇴 시 본인 흔적만 삭제** — 그가 담은 공유작품·누른 좋아요·쓴 댓글. 그가 담은 작품에 **남이 누른 좋아요도 함께** 사라진다(대상이 없어지므로).
- **삭제 순서는 FK 역순** — 댓글 → 좋아요 → 공유작품 → 멤버 → 보드.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 공유작품을 `(보드, 작품)` 단위 한 행 + 담은 사람 목록 | **"누가 담았는지"가 사라진다.** 담은 사람만 자기 후보를 수정할 수 있어야 하는데 소유자를 특정할 수 없다 |
| **참여자마다 한 행 + 조회에서 중복 제거** | **최초 채택안. 아래 번복 절에서 기각** |
| 댓글을 공유작품 단위로 | 화면이 작품 카드 그리드라 카드마다 댓글 스레드를 열 자리가 없다. 기획도 보드 단위 대화 |
| 방장도 나갈 수 있게 하고 자동 위임 | 일반 탈퇴 경로에까지 위임 로직이 들어간다. 방장은 삭제로 끝내고, **위임은 회원 탈퇴에서만** 처리 |
| 방장에게 멤버 강퇴·초대 독점 권한 | 친구끼리 쓰는 보드라 권한 계층이 과하다. 초대는 열고 파괴적 동작만 방장으로 제한 |

## 결정 번복 (2026-08-13)

최초에는 **참여자마다 한 행**(unique `(board, artwork, customer)`)으로 두고 조회 시 작품 단위로 합쳤다. "3명이 같은 작품을 담았다"가 의사결정 신호가 된다고 봤기 때문이다.

**실제로 만들어보니 그 신호는 좋아요가 이미 하고 있었고, 대신 비용만 남았다.**

- 조회할 때마다 `toMap` 으로 **대표 행을 뽑는 중복 제거**가 필요했다.
- 좋아요를 공유작품이 아니라 **작품 단위로 합산**해야 해서, 집계·"내가 좋아요했는지" 판정이 전부 `artworkId` 를 경유하는 우회를 탔다.
- 응답의 공유작품 ID 가 "가장 먼저 담긴 행"이라는 **설명이 필요한 값**이 됐다.
- 화면은 어차피 카드 하나로 보여주는데, 저장 목록에서 "이미 담긴 작품"의 체크 상태를 어떻게 보일지가 계속 애매했다.

번복 후:
- 중복 제거 로직 삭제, 좋아요 집계·조회가 **공유작품 단위로 직행**.
- 저장 작품 조회에 **`sharedBy`**(담은 참여자: 고객 ID / 이름 / 프로필 색상)를 추가. **아무도 안 담았으면 `null`** 이라, 프론트가 `null` 여부만으로 선택 가능 여부를 판정한다.

> [!warning] 배포 시 확인
> 기존 데이터에 `(shared_board_id, artwork_id)` 중복 행이 있으면 새 unique 생성이 실패한다. 정리 후 옛 인덱스 `uk_shared_artwork_board_artwork_customer` 도 **수동 드롭**해야 한다 — `ddl-auto: update` 는 인덱스를 지우지 않는다.

## 결과 (트레이드오프)
- ✅ 조회 경로에서 중복 제거·작품 단위 합산이 사라져 코드가 단순해졌다.
- ✅ 좋아요 수가 정렬에 이미 필요해 집계되므로, 응답에 싣는 데 **추가 쿼리가 없다.**
- ✅ 방장이 참여자 행에 포함돼 멤버 조회·인원수에 분기가 없다.
- ⚠️ **먼저 담은 사람이 임자다.** 다른 참여자는 그 작품을 담을 수 없고, 담은 사람이 빼면 보드에서 사라진다.
- ⚠️ 내가 담은 작품을 빼면 **남이 그 작품에 누른 좋아요도 사라진다.**
- ⚠️ 정원 제한이 없다. 초대 코드를 아는 사람이 무제한 들어온다([[ADR-017 공동보드 초대 링크 - PK 대신 초대 코드]] 후속).
- ⚠️ 작가 프로필만 있는 계정은 참여할 수 없다(`@CurrentCustomer`). 프론트가 "고객 프로필이 필요해요"로 안내해야 한다.
