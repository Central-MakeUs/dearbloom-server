> **ADR-019 · Domain · Accepted · 2026-08-10**
> 작가가 등록한 작품 패키지를 나중에 수정할 수 있게 하면서, 패키지를 지우면 문의가 작가를 잃어버리던 구조를 고친다. → **`Inquiry` 가 작가·작품을 직접 FK 로 참조하고(artist 는 NOT NULL·절대 안 끊김), 패키지 수정은 별도 엔드포인트에서 soft delete 없이 통째 교체한다.**

## 맥락

패키지는 그동안 **작품 등록 시점에만** 만들어지고 수정 경로가 없었다. 수정 대상이 되는 순간, 드러나 있지 않던 참조 구조의 문제가 걸렸다.

`Inquiry` 는 당사자를 **비대칭적으로** 잡고 있었다.

```
Inquiry ──customer_id──────────────────────────────► Customer   (직접 FK)
Inquiry ──artwork_package_id──► ArtworkPackage ──► Artwork ──► Artist   (3-hop)
```

작가 쪽 조회는 전부 이 3-hop 경로를 탔다. JPQL 경로 탐색은 **암묵적 INNER JOIN** 이라 `artwork_package_id` 가 NULL 이면 그 문의는 결과에서 그냥 빠진다.

| 조회 | 문의가 빠지면 |
|---|---|
| `findByArtistOrderByShootDateAsc` | 작가 문의함에서 증발 |
| `findByArtistAndShootDateAndStatus` | **예약 확정 슬롯 계산에서 누락 → 잡힌 시간이 다시 열림** |
| `findByArtistAndShootDateBetweenAndStatus` | 캘린더 동일 |
| `findByArtistIdAndStatusIn` | 탈퇴 시 자동 취소 대상에서 누락 |
| `ChatFacade.onInquiryCreated` | `getArtworkPackage().getArtwork().getArtist()` — NPE 위험 |

패키지를 지우려면 FK 때문에 문의의 참조를 먼저 끊어야 하는데, 끊는 순간 위가 전부 무너진다. **작가가 패키지 이름 오타 하나 고쳤을 뿐인데 예약된 시간대가 풀려 중복 예약이 가능해진다.** 슬롯 잠금을 `status=RESERVED` 문의로 계산하는 구조([[ADR-009 스마트 문의·예약 - 상태 단일화와 슬롯 잠금]])라 조회에서 빠지는 것이 곧 잠금 해제다.

이 결함은 패키지 수정 이전에도 **이미 있었다.** `ArtworkCommandFacade.delete` 가 문의 상태를 보지 않고 `detachArtworkPackage()` 를 호출하므로, 예약 완료된 문의가 달린 작품을 삭제하면 그 시점에 슬롯이 풀렸다. ADR-009 갱신분에서 `artworkPackage` 를 nullable 로 완화하며 "문의는 참조만 끊고 유지"를 택했는데, 그 판단은 **표시(스냅샷) 관점에서만** 옳았고 구조적 링크 관점은 검토되지 않았다.

고객 쪽에는 이 문제를 우회한 흔적이 이미 있었다 — 목록 쿼리의 `left join fetch i.artworkPackage`. 고객은 `customer_id` 라는 독립 컬럼이 있어 LEFT JOIN 으로 해결됐지만, **작가는 식별자 자체를 끊긴 경로에서 읽어야 해서 같은 수를 쓸 수 없었다.** 이 비대칭이 문제의 본질이다.

## 결정

### 1. 문의가 작가·작품을 직접 FK 로 참조

| 필드 | 제약 | 끊기는 시점 |
|---|---|---|
| `artist` | **NOT NULL** | 없음 — 어떤 경우에도 끊지 않는다 |
| `artwork` | nullable | 작품 삭제 |
| `artworkPackage` | nullable | 작품 삭제 / 패키지 교체 |

`artist` 를 NOT NULL 로 둘 수 있는 근거는 작가 탈퇴가 행을 지우지 않고 `Artist.anonymize()` 로 익명화하기 때문이다([[ADR-010 회원 탈퇴·역할 해지 - soft delete·익명화·문의 자동취소]]). 참조가 깨질 일이 없다.

3-hop 경로 탐색은 전부 제거.

```java
where i.artworkPackage.artwork.artist.artistId = :artistId   →   where i.artist.artistId = :artistId
```

`getArtworkOrNull()` / `getArtworkIdOrNull()` 이 `artwork` 필드를 읽도록 바꾸면서, 이 둘을 거치는 소비자(문의 목록·상세·채팅 카드)는 손대지 않았다. 고객 목록 fetch join 도 `left join fetch i.artworkPackage p / left join fetch p.artwork` 두 줄에서 `left join fetch i.artwork` 한 줄로 줄었다.

`detachArtworkPackage()` 를 두 갈래로 나눈다.

- `detachArtwork()` — 작품 삭제용. `artwork` + `artworkPackage` 를 끊는다.
- `detachArtworkPackage()` — 패키지 교체용. `artworkPackage` 만 끊는다.

### 2. 패키지 수정은 별도 엔드포인트에서 목록 통째 교체

```
PUT /api/artworks/{artworkId}/packages
```

`PATCH /{artworkId}`(작품명·설명 부분 수정)에 합치지 않는다. 성격이 다르고 — 한쪽은 보낸 필드만 바꾸고 다른 쪽은 목록 전체를 대체한다 — 무엇보다 **패키지가 바뀌면 `Artwork.lowestPrice` 를 반드시 재계산해야 하는 불변식**이 "패키지를 보냈는가" 조건문 속으로 숨는다. 이미 사진 교체(`PUT /{artworkId}/photos`)가 같은 자리에 같은 성격으로 있어 형태도 맞다.

실행 순서 — 한 트랜잭션:

```java
Artwork artwork = artworkQueryService.getOwnedBy(artworkId, artist);      // 소유권 검증
inquiryCommandService.detachArtworkPackages(artwork);                     // 참조 해제 + flush
artworkCommandService.replacePackages(artwork, newPackages, lowestPrice); // 삭제 → 가격 갱신 → 저장
```

`detach` 뒤에 **명시적 `flush()`**. Hibernate 가 UPDATE 를 DELETE 보다 먼저 내보내는 게 기본 동작이지만, FK 제약이 걸린 삭제가 내부 액션 큐 순서에 암묵적으로 기대게 두지 않는다.

`lowestPrice` 재계산은 `ArtworkCommandService.replacePackages` **안에** 넣는다. 패키지를 갈아끼우는 코드와 가격을 갱신하는 코드가 떨어져 있으면 언젠가 한쪽만 호출된다.

### 3. 보정본 수 스냅샷 추가

`Inquiry.finalPhotoCountSnapshot` (nullable — 패키지의 "미정"과 같은 의미).

문의 상세는 패키지명·가격·촬영 소요시간을 스냅샷으로 보여주는데 보정본 수만 빠져 있었다. 패키지가 수정 가능해지면 이 값은 **복구 불가능하게** 사라진다 — 작가가 예약 후 "보정본 10장 → 5장" 으로 바꿔도 합의 내용이 어디에도 남지 않는다. 고객·작가 문의 상세 응답에 `finalPhotoCount` 로 노출(필드 추가라 기존 프론트 영향 없음).

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| `ArtworkPackage` soft delete (삭제 플래그) | 문의 FK 가 안 끊겨 매력적이지만, 패키지를 읽는 모든 곳에 `deleted = false` 를 붙여야 하고 빠뜨리면 조용히 샌다. FK 를 제대로 박으면 영구적으로 단순해지는데 굳이 플래그를 들일 이유가 없다. 등록 로직(`deleteByArtwork` + `saveAll`) 재사용도 못 한다 |
| ID 기반 upsert (있으면 UPDATE, 없으면 INSERT, 빠진 건 DELETE) | 프론트가 패키지 ID 를 들고 다녀야 하고, 참조 중인 패키지가 제거 대상이면 결국 soft delete 폴백이 필요하다. 현재 규모에서 얻는 게 없다 |
| `artist` FK 만 추가 | 작가 조회 4개는 안전해지지만, 패키지 교체 때 `artworkPackage` 를 끊으면 고객 문의 목록의 "작품 상세로 이동" 링크가 죽는다. 작품은 멀쩡히 살아있는데도 |
| `artwork` FK 만 추가 | 작품이 삭제되면 `artwork` 가 NULL 이 되고 작가 조회가 다시 무너진다. 채택 불가 |
| 패키지 수정을 `PATCH /{artworkId}` 에 합치기 | 부분 수정과 전체 교체가 한 엔드포인트에 섞이고, `lowestPrice` 재계산 트리거가 조건문 속으로 숨는다 |

## 결과 (트레이드오프)

- ✅ 패키지를 어떻게 건드려도 작가 문의함·예약 확정 슬롯 계산·캘린더·작품 상세 이동이 안전하다.
- ✅ **기존 버그가 함께 닫혔다** — 예약 완료 문의가 달린 작품을 삭제해도 이제 슬롯이 풀리지 않는다.
- ✅ 3-hop 조인 5개가 컬럼 비교로 바뀌었다. `ChatFacade` 의 NPE 위험 경로도 사라졌다.
- ✅ `artist_id NOT NULL` 로 "문의는 반드시 작가에게 속한다"가 스키마 수준 불변식이 됐다.
- ⚠️ `inquiry` 에 컬럼 3개 추가(`artist_id`, `artwork_id`, `final_photo_count_snapshot`). 문의 생성 시 세팅할 값이 늘었지만 `CustomerInquiryFacade` 가 이미 두 엔티티를 손에 들고 있어 실제 추가는 두 줄.
- ⚠️ 패키지 교체마다 그 작품의 문의를 전부 로드해 참조를 끊는다. 작품당 문의가 많아지면 부담이지만 패키지 수정은 드문 작업이라 현재 규모에서 문제되지 않는다.
- ⚠️ `artworkPackage` FK 는 남겨뒀다. 표시값은 전부 스냅샷이 들고 있어 구조적 역할이 사실상 없지만, 지우는 건 별도 판단.
- ⚠️ **`ArtworkCommandFacade.delete` 는 여전히 예약 완료(RESERVED) 문의가 있어도 작품 삭제를 막지 않는다.** 이제 슬롯은 유지되지만 고객이 예약한 작품 자체는 사라진다(기록은 스냅샷으로 남음). 막을지는 기획 판단이라 이 ADR 범위 밖.
