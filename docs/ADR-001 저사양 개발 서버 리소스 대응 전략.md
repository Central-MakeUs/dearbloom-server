> **ADR-001 · Infra/Ops · Accepted · 2026-07 (개발 서버 구성 시점)**
> 저사양 단일 개발 서버에 Spring Boot·MySQL·Redis 등을 함께 올려 구동하기 위해, 무엇을 의도적으로 줄이고 끌지에 대한 방침. → **관측성·빌드캐시·DB 리소스를 개발 환경 한정으로 축소하고, 부족한 메모리는 스왑으로 보완.**

## 맥락
- 개발 서버는 **저사양 단일 인스턴스**에 앱 + MySQL + Redis 등을 함께 올려 돌린다(비용 절감).
- 기본 설정(관측성 풀활성, DB 버퍼 크게, 빌드 캐시 등)으로는 **메모리 압박·OOM·빌드 실패** 위험.
- 개발 서버는 "동작 확인·통합 테스트"가 목적이지 **성능·관측성 자체가 목적이 아니다.**

## 결정
개발 환경에 한해 아래를 **의도적으로 축소/비활성화**한다:
- **관측성**: Spring Boot **OTLP 메트릭 전송 off**(불필요한 상시 push 제거).
- **빌드**: Gradle **빌드 캐시/데몬 등 메모리 사용 제한**.
- **DB**: MySQL 각종 버퍼/커넥션 등 **리소스 상한 축소**, 불필요 기능 off.
- **메모리**: 부족분을 **스왑(swap)** 으로 보완해 OOM 회피.

→ 운영(prod) 환경에는 **적용하지 않는다.** 이 방침은 dev 전용.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 서버 스펙 업(증설) | 개발 단계 비용 부담, 지금 목적엔 과함 |
| 관측성 풀 유지 + 별도 관측 서버 | 인프라·비용 증가, 개발 단계에 불필요 |
| 기본 설정 그대로 | 저사양에서 OOM/빌드 실패로 구동 자체가 불안정 |
| 컨테이너별 리소스 분리(각각 다른 인스턴스) | 비용↑, 개발용으론 과투자 |

## 결과 (트레이드오프)
- ✅ 저사양 단일 서버에서 전체 스택을 안정적으로 구동.
- ✅ 비용 최소화.
- ⚠️ **개발 서버엔 상세 메트릭/프로파일링이 없음** — 성능 이슈 재현·관측이 어려움(의도된 포기).
- ⚠️ **스왑 의존**은 지연(latency) 증가 유발 → 성능 수치를 개발 서버에서 신뢰하면 안 됨.
- ⚠️ dev/prod 설정 분기가 존재 → prod에 dev 축소 설정이 새지 않도록 프로파일 관리 필요.

## 부록 — 구체 수치(런북)
> 자주 바뀌는 값이라 ADR 본문이 아니라 부록/인프라 레포에서 관리. (dearbloom-infra 참고, 직접 편집 금지)
- Gradle: 캐시/데몬/힙 옵션 값
- MySQL: `innodb_buffer_pool_size`, `max_connections` 등
- OTLP: 비활성 플래그/엔드포인트
- Swap: 크기·swappiness

## 상태
Accepted (dev 한정). 운영 확장 시 관측성 재활성/서버 증설로 **재검토(Supersede) 대상**.
