> **ADR-025 · Infra · Accepted · 2026-08-18**
> 앱을 켜면 모두가 지나는 작품 탐색 목록을 캐시할지, 한다면 어디까지 할지 결정. → **파라미터가 하나도 없는 "첫 화면" 하나만 단일 Redis 키로 캐시한다. `isSaved` 는 담지 않고 조회 시점에 덧씌워 로그인 사용자도 같은 캐시를 탄다. 무효화는 커밋 후 이벤트로 즉시, TTL 10분은 신선도가 아니라 실수 대비 바닥이다.**

## 맥락
- 작품 탐색 목록은 **모든 방문자가 앱을 켜면 반드시 통과하는 유일한 쿼리**다.
- 그런데 그 쿼리는 가볍지 않다 — 날짜를 요일로 접는 EXISTS, 지역·인원 EXISTS, 정렬, 커서 페이지네이션이 다 붙는다([[ADR-020 작품 탐색 - 날짜를 요일로 접는 필터 + 커서 페이지네이션]]).
- 다행히 **첫 진입은 형태가 하나로 고정**된다. 파라미터 없이 최신순 첫 페이지, 크기는 16 고정(요청으로 조절하지 않는다). 필터·정렬 UI 를 건드려야 비로소 조합이 생긴다.
- 반면 `isSaved`(내가 저장했는지)는 **사람마다 다르다.** 이걸 어떻게 다루느냐가 캐시 설계 전체를 가른다.

## 결정
### 무엇을 캐시하나 — 첫 화면 하나, 키도 하나
```
artwork:explore:v1:first-page      TTL 10분
```
- 필터를 넣으면 **날짜 × 지역 × 인원 × 정렬 × 커서**로 조합이 폭발한다. 적중률은 낮고 무효화 대상만 는다.
- `v1` 은 **응답 스키마 버전**이다. `ArtworkPageResponse` / `ArtworkSummaryResponse` 필드가 바뀌면 올린다 — 구버전 JSON 이 남아 있어도 역직렬화가 깨지지 않고 그냥 미스가 된다.

### `isSaved` 는 캐시에 담지 않는다
- 담는 값은 `isSaved` 가 전부 null 인 **"사람과 무관한 페이지"** 다. 담으면 남의 저장 상태가 그대로 나간다.
- 조회 시점에 저장 목록을 한 번 읽어 각 항목에 덧씌운다.
- 덕분에 **로그인 사용자도 비로그인과 같은 캐시를 탄다.** 사용자별 키를 만들 필요가 없다.

### 무효화 — `AFTER_COMMIT`, 동기, 삭제
- **`AFTER_COMMIT` 이어야 한다.** 트랜잭션 안에서 지우면 이 순서가 가능하다.
    1. 트랜잭션이 캐시를 지운다
    2. 다른 요청이 미스 → DB 조회 → **아직 커밋 안 된 변경을 못 본다** → 옛 목록을 캐시에 쓴다
    3. 트랜잭션이 커밋된다
    4. **이걸 고칠 이벤트는 더 이상 없다** → TTL 까지 낡은 채로 남는다
- **`@Async` 를 붙이지 않는다.** 메일·푸시 리스너와 달리 하는 일이 키 하나 삭제라 즉시 끝난다. 비동기로 미루면 커밋과 삭제 사이 간격만 넓어져 그동안 낡은 목록이 나간다.
- **갱신(refresh)이 아니라 삭제(evict).** 프론트에서 작품 등록 한 번이 API 3~4번이다(작품 생성 → 사진 교체 → 패키지 교체). 갱신 방식이면 등록 한 번에 목록을 그만큼 다시 계산한다. 삭제는 멱등하고 공짜이며, 다음 조회가 한 번만 채운다.

무효화 지점은 **카드에 보이는 값을 바꾸는 모든 경로**다 — 작품 생성·이름·사진·패키지·삭제(`ArtworkCommandFacade` 5곳), 작가 닉네임·활동지역(`ArtistFacade` 2곳), 회원 탈퇴(`MemberFacade`).

### TTL 10분의 의미
**신선도용이 아니다.** 무효화가 커밋 후 즉시 일어나므로 평상시 TTL 이 발동할 일이 없다. **새 무효화 지점을 빠뜨린 코드가 들어왔을 때 최대 10분이면 스스로 낫도록 두는 바닥**이다.
(첫 화면 쿼리에는 날짜 조건이 붙지 않아 시계에 의존하지 않는다 — 시간이 흘러도 결과가 바뀌지 않으므로 TTL 을 짧게 둘 이유가 없다.)

### Redis 장애가 조회를 막지 않는다
읽기 실패는 **캐시 미스**로 처리해 DB 로 내려가고, 쓰기·삭제 실패는 로그만 남긴다. 캐시는 없어도 되는 것이고, 목록 조회는 없으면 안 되는 것이다.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| `@Cacheable` 로 필터 조합까지 전부 캐시 | 조합이 폭발한다. 적중률은 낮고 무효화 대상만 는다 |
| `isSaved` 까지 담고 사용자별 키 | 사용자 수만큼 키가 생기고, 무효화가 **전수 삭제**가 된다 |
| 트랜잭션 안에서 evict | 커밋 전 상태를 읽은 요청이 옛 목록을 다시 채우고, **그걸 고칠 이벤트가 더 없다** |
| evict 를 `@Async` 로 | 커밋과 삭제 사이에 낡은 목록이 나간다. 얻는 건 키 삭제 한 번의 지연 제거뿐 |
| evict 대신 refresh(즉시 재계산) | 등록 한 번에 목록을 3~4번 다시 계산한다 |
| TTL 만으로(이벤트 없이) | 작품을 올려도 최대 10분간 목록에 안 보인다 |
| TTL 없이 이벤트만 | 무효화 지점을 하나라도 빠뜨리면 **영구히** 낡는다 |
| 로컬 캐시(Caffeine) | 인스턴스가 늘면 인스턴스마다 다른 목록이 나간다 |
| 캐시 없이 인덱스·쿼리 튜닝만 | 해야 하지만 별개다. 첫 화면은 튜닝해도 전원이 통과하는 유일한 지점이라 캐시 이득이 가장 크다 |

## 결과 (트레이드오프)
- ✅ 앱 진입의 유일한 공통 쿼리가 **Redis 조회 한 번**으로 끝난다.
- ✅ 로그인·비로그인이 **같은 캐시**를 쓴다.
- ✅ Redis 가 죽어도 목록은 나온다.
- ⚠️ **무효화 지점이 코드에 흩어져 있다.** 지금 3개 파사드 9곳. 카드에 새 필드가 생기면 **그 필드를 바꾸는 모든 경로에 이벤트를 추가**해야 하고, 빠뜨리면 최대 10분 낡는다. 컴파일러도 테스트도 이걸 잡아주지 않는다.
- ⚠️ **첫 화면 정의(`ArtworkQueryRequest#isFirstScreen`)가 바뀌면 캐시 적중이 조용히 0이 된다.** 성능이 나빠질 뿐 기능은 멀쩡해서 눈치채기 어렵다.
- ⚠️ 응답 DTO 를 바꾸고 **`v1` 을 안 올리면** 역직렬화 실패가 로그로만 남고 계속 미스가 난다.
- ⚠️ 캐시된 `totalCount` 도 함께 낡는다 — 목록과 개수가 같은 시점의 값이라 서로 어긋나진 않는다.
- ⚠️ 캐시를 타는 응답과 안 타는 응답의 **지연 차이가 크다.** 필터를 한 번 건드리면 체감이 달라진다.
