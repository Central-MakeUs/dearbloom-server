> **ADR-005 · Domain · Accepted · 2026-07-19**
> 작품 조회(리스트·상세)를 비로그인/고객/작가 뷰어에 따라 어떻게 응답할지 결정. → **토큰 activeRole 기준 분기. 공개/고객은 단일 엔드포인트, 작가 본인은 별도 엔드포인트.**

## 맥락
- 같은 작품 리소스를 **비로그인 / 고객 / 작가 본인**이 본다.
- 뷰어별 노출 정보가 다르다: 고객은 **저장 여부(isSaved)**, 작가 본인은 **저장 수/조회수(savedCount/viewCount)**, 비로그인은 기본 정보만.
- 겸용 계정(고객∧작가)은 **"현재 어떤 역할로 접속했는지"** 로 갈려야 한다(사람 신원이 아니라).

## 결정
- **공개/고객 상세** `GET /api/artworks/{id}` — `@CurrentViewer`(비로그인 허용). 고객 토큰이면 `isSaved` 채움. 응답 `ArtworkDetailResponse`.
- **작가 본인 상세** `GET /api/artists/me/artworks/{id}` — `@CurrentArtist` + 소유권 검증. 응답 `ArtistArtworkDetailResponse`(savedCount/viewCount).
- **리스트**도 동일하게 분리: 공개/고객 `ArtworkSummaryResponse`(isSaved), 작가 본인 `ArtistArtworkSummaryResponse`(savedCount/viewCount).
- 판정 기준은 **member 신원이 아니라 토큰의 `activeRole`/`activeProfileId`** (`@CurrentViewer` 가 제공).

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 단일 URL + 폴리모픽 응답(뷰어 따라 다른 스키마) | 프론트가 응답 타입 분기해야 함, 계약 불명확 |
| 단일 DTO + 뷰어 필드 전부 nullable(isMine/savedCount/isSaved) | "어느 필드가 누구용"이 암묵적, 작가/고객 화면이 실제로 다름 |
| member 신원으로 isSaved 판정 | 겸용 계정이 작가로 봐도 고객 저장여부가 딸려옴(버그) |
| 역할별 URL 3개 | 공통 필드 중복·라우팅 복잡 |

## 결과 (트레이드오프)
- ✅ 공개 상세 계약이 깔끔(isMine 플래그 제거). 작가는 전용 URL 로 진입 → activeRole 분기 로직 최소화.
- ✅ 겸용 계정도 접속 역할대로 정확히 갈림.
- ⚠️ DTO/엔드포인트가 뷰어별로 늘어남(공개용·작가용). 매핑 일부 중복(스키마 헬퍼로 공유).
- ⚠️ N+1 방지 위해 리스트는 fetch join + `@BatchSize`(regions) + 대표이미지 배치 필요.

## 관련
- `domain/artwork/facade/ArtworkQueryFacade`, `ArtworkController`, `ArtistController#getMyArtwork(s)`
- `ArtworkDetailResponse`/`ArtistArtworkDetailResponse`, `ArtworkSummaryResponse`/`ArtistArtworkSummaryResponse`
