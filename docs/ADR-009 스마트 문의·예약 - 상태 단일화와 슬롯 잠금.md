> **ADR-009 · Domain · Accepted · 2026-07-24**
> 스마트 문의~예약의 상태·엔티티를 어떻게 둘지 결정. → **문의 4상태를 `Inquiry.status` 단일 소스로 관리, 별도 Reservation/슬롯잠금 테이블 없이 status=RESERVED 로 슬롯을 잠그고, 상태 변경은 `InquiryHistory` 로 append-only 기록.**

## 맥락
- 결제가 없어 **예약 완료가 종착 성공 상태**다([[결제 없음·예약 완료가 마지막]]). 상태 그래프가 짧다: 문의 진행중 → (예약 완료 → 예약 취소) / (문의 취소).
- 문의는 스냅샷 기반이어야 한다 — 작가가 작품/패키지를 수정·삭제해도 문의 기록은 시점 값을 보존.
- 예약 완료 시 작가 일정 슬롯이 닫히고, 예약 취소 시 열려야 한다([[ADR-008 작가 일정 관리 - 규칙 기반 가용성(sparse + 비트마스크)]] 의 booked 계산과 맞물림).

## 결정
- **상태 단일 소스** — `Inquiry.status ∈ {IN_PROGRESS, INQUIRY_CANCELED, RESERVED, RESERVATION_CANCELED}`. 예약 완료/취소도 이 필드로 표현. 전이 가드는 엔티티 메서드(`reserve`/`cancelReservation`/`cancelAsInquiry`)에 둔다.
- **Reservation 엔티티 제거** — 상태·촬영정보·스냅샷을 전부 Inquiry 가 소유하므로 예약 전용 엔티티가 값을 못 한다. "예약 완료 시각"은 `InquiryHistory` 의 `toStatus=RESERVED` 행 createdAt 으로 얻는다.
- **슬롯 잠금 = status** — 별도 예약확정 셀 테이블 없이, **status=RESERVED 문의**를 booked 로 계산(`InquiryBookedSlotProvider` adapter). 예약 완료=잠김, 취소=자동 해제. 예약 완료 시 다른 booked 와 겹치는지 재검증(중복 방지).
- **문의는 슬롯 잠금 안 함** — 문의=제안. 잠금은 예약 완료 시점에만.
- **상태 변경 이력** — `InquiryHistory(fromStatus, toStatus, changedByRole)` append-only. 전이 직후 1행 기록. 작가용 타임라인 조회 API 제공. 문의 취소는 고객·작가 둘 다, 예약 완료·취소는 작가만.
- **스냅샷** — 작가 닉네임/작품명/패키지명/가격/소요시간 + 학교명을 문의 시점에 Inquiry 에 복사(flat 컬럼). 학교는 `university` FK(목록 선택) 또는 자유입력 `schoolName` 둘 중 하나.
- **컨트롤러·파사드 고객/작가 분리** — Customer/Artist InquiryController·Facade. 조회는 고객 리스트=최근수정순, 작가 리스트=촬영일순.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 상태를 Inquiry {진행중,취소} + Reservation {확정,취소} 로 분리(파생) | 결제 없어 상태 짧음. 고객 목록이 매번 조인/파생 필요. "문의 4상태" 모델과 어긋남 |
| Reservation 을 예약 확정 레코드로 유지 | 링크+타임스탬프뿐이라 빈 껍데기. 예약완료 시각은 이력으로 대체 가능 → 삭제 |
| 예약확정 셀 unique 잠금 테이블 | 예약 완료는 단일 액터(작가)라 동시성 낮음. status=RESERVED 로 계산하면 테이블/삭제로직 없이 잠금/해제 공짜 |
| 이력에 fromStatus 없이 toStatus 만 | 각 행을 자기완결적("진행중→예약완료")으로 표시하려면 fromStatus 유지가 편함 |

## 결과 (트레이드오프)
- ✅ 상태·촬영정보·스냅샷·이력이 Inquiry 중심으로 모여 단순. 화면 간 불일치 없음.
- ✅ 슬롯 잠금/해제가 status 하나로 표현 → 잠금 테이블·삭제 로직 불필요.
- ✅ 스냅샷으로 작가 수정/삭제와 무관하게 문의 기록 보존.
- ⚠️ 예약 완료 중복 방지가 **check-then-set**(단일 작가라 실무상 안전, 하드 DB 잠금 아님). 멀티 액터로 커지면 unique 테이블 재도입 여지.
- ⚠️ 전이+이력 append 가 한 트랜잭션 → **이력 INSERT 실패 시 상태 전이도 롤백**. (실제로 `inquiry_history` 옛 stale 컬럼 `customer_id NOT NULL` 때문에 전이가 통째 실패한 사건 있었음 → ddl-auto:update 가 컬럼을 안 지우는 함정. 재발 시 stale 컬럼 정리 필요.)

## 갱신 (2026-08-09)

### 작품 삭제와 스냅샷 — FK 완화 (`4a5ea41`)

스냅샷 결정("작품이 삭제돼도 문의는 유지")을 **스키마가 따라가지 못하고 있었다.** `Inquiry.artworkPackage` 가 NOT NULL FK 라, 문의·저장·신고가 하나라도 달린 작품은 삭제가 FK 제약 위반으로 실패했다.

- `Inquiry.artworkPackage` 를 **nullable 로 변경** + `detachArtworkPackage()` / `getArtworkOrNull()` / `getArtworkIdOrNull()` 추가. 문의 행은 스냅샷으로 보존한다.
- 작품 삭제 시 참조를 먼저 정리 — `SavedArtwork`·`Report` 는 **삭제**(대상이 사라지면 무의미), `Inquiry` 는 **참조만 끊고 유지**(상대방의 거래 이력).
- 문의 상세·문의 카드의 `artworkId` 를 nullable 로 노출(삭제된 작품이면 null).
- 고객 문의 목록 쿼리를 `left join fetch` 로 수정 — inner 라서 작품이 삭제되면 **그 문의가 목록에서 통째로 사라지던 버그**가 있었다.
- 작가 문의 접근 검증은 작품이 없으면 소유자 확인 불가로 보고 거부.

이 정리 덕분에 회원 탈퇴 시 작가의 작품을 통째로 지울 수 있게 됐다([[ADR-010 회원 탈퇴·역할 해지 - soft delete·익명화·문의 자동취소]] 갱신분).

### 고객 문의 목록 정렬 변경

`modifiedAt desc` → **`createdAt desc, inquiryId desc`**(신청 최근순). 상태가 바뀔 때마다 순서가 올라가면 응답의 `requestedAt`(문의 신청 시각)과 목록 순서가 어긋나 보이기 때문. `createdAt` 이 초 단위라 같은 초에 들어온 문의의 순서가 흔들리지 않도록 PK 로 tie-break 한다.

작가 목록은 그대로 **촬영일 오름차순**이다(다가오는 촬영 순). 이전에 DTO 주석이 "최근 수정순"이라고 잘못 적혀 있던 것을 실제 동작에 맞춰 고쳤다.

### 문의 생성 응답에 채팅방 ID 추가

문의를 보내면 채팅방에 문의 카드가 쌓이는데 응답에 방 ID 가 없어 프론트가 그 방으로 이동할 수 없었다. 문의 → 채팅은 `InquiryCreatedEvent` 로 단방향 분리돼 있어(채팅이 문의를 알고, 문의는 채팅을 모른다) 파사드에서 `ChatFacade` 를 직접 부르면 순환 의존이 된다. **이벤트가 결과를 되받는 형태**로 처리했다 — 동기 리스너라 `publishEvent` 직후 발행 측에서 읽을 수 있다.

⚠️ 리스너를 `@Async` 나 `AFTER_COMMIT` 으로 바꾸면 `chatRoomId` 가 **조용히 null** 이 된다.
