> **ADR-006 · Auth · Accepted · 2026-07-13 ~ 2026-07-19**
> dearbloom 서버. 하나의 `Member`가 고객/작가 역할을 겸할 수 있는 Party-Role 구조에서, 컨트롤러가 "지금 어떤 역할로 접속했는지"를 어떻게 주입받을지에 대한 설계 결정. `@CurrentArtist` / `@CurrentCustomer` / `@CurrentViewer` 3종 argument resolver로 정리됨.

---

## 1. 배경

- 한 `Member`가 `hasCustomer` / `hasArtist` 플래그로 **고객·작가 프로필을 동시에** 가질 수 있음 (Party-Role 패턴).
- Access Token 클레임에 `activeRole`(CUSTOMER/ARTIST) 과 `activeProfileId`(그 역할의 PK = customerId 또는 artistId) 를 담음. → "지금 어느 역할 모드로 접속 중인가"가 토큰에 있음.
- `TokenAuthenticationFilter` 가 인증을 `UsernamePasswordAuthenticationToken(member, token, authorities)` 로 심음.
  - **principal = `Member` 엔티티**, **credentials = 원본 JWT 문자열**.
  - 덕분에 리졸버가 토큰을 다시 헤더에서 파싱할 필요 없이 SecurityContext의 credentials에서 꺼내 씀 (`CurrentProfileTokenSupport.extractToken`).

## 2. 문제

- API마다 요구하는 "뷰어 조건"이 다름:
  - 작가 전용 API (작가 프로필 필요, 역할 강제).
  - 고객 전용 API (고객 프로필 필요, 역할 강제).
  - **공개 조회 API** — 비로그인/고객/작가 **누구나** 접근하되, 역할에 따라 응답만 달라짐 (예: 작품 상세조회의 `savedCount`/`isSaved`).
- `@AuthenticationPrincipal Member` 만으로는 **"지금 어떤 역할(activeRole)로 접속했는지"** 를 알 수 없음 → 겸용 계정에서 오작동.

## 3. 결정 — 리졸버 3종

| 애노테이션 | 주입 타입 | 역할 불일치 시 | 비로그인 | 용도 |
|---|---|---|---|---|
| `@CurrentArtist` | `Artist` | **403** (ROLE_ACCESS_DENIED) | 막힘 | 작가 전용 API |
| `@CurrentCustomer` | `Customer` | **403** | 막힘 | 고객 전용 API |
| `@CurrentViewer` | `ViewerContext` | 안 막음 | 허용(guest) | 공개 조회 API (역할별 응답 분기) |

- `@CurrentArtist`/`@CurrentCustomer`: **문지기**. `activeRole` 검사 → 불일치면 403. `activeProfileId` 로 해당 프로필 엔티티 조회해 주입.
- `@CurrentViewer`: **라벨러**. 막지 않고 `ViewerContext(member, activeRole, activeProfileId)` 를 담아 주입. 비로그인이면 `ViewerContext.guest()`(전부 null), 예외 없음.

```java
public record ViewerContext(Member member, MemberRole activeRole, Long activeProfileId) {
    boolean isArtist()   { return activeRole == ARTIST   && activeProfileId != null; }
    boolean isCustomer() { return activeRole == CUSTOMER && activeProfileId != null; }
}
```

## 4. 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| `@CurrentArtist`/`@CurrentCustomer` 만으로 공개 조회까지 처리 | 역할 강제(403)라 비로그인/타역할이 막힘 |
| `@AuthenticationPrincipal Member` + `findByMember` 로 역할 판정 | member 신원 기준이라 겸용 계정에서 오작동(아래) |
| 컨트롤러마다 토큰 직접 파싱 | 중복·산발, 리졸버로 일원화가 나음 |

### 왜 "member 신원"이 아니라 "activeRole" 기준인가
초기 구현은 상세조회에서 `findByMember(member)` 로 고객 프로필을 찾아 `isSaved` 를 채웠음. **문제**: 겸용 계정이 **작가 토큰으로 조회해도** 그 member의 고객 프로필이 있으면 `isSaved` 가 딸려옴 → "작가로 보는데 고객 저장여부 노출".
→ 판정 기준을 **member 신원 → 토큰의 activeRole** 로 전환. `@CurrentViewer` 가 activeRole/activeProfileId를 넘겨줘 facade가 정확히 분기.

```java
boolean isArtworkOwner = viewer.isArtist()
        && artist.getArtistId().equals(viewer.activeProfileId());
Boolean isSaved = viewer.isCustomer()
        ? savedArtworkQueryService.isSaved(viewer.activeProfileId(), artworkId)
        : null;
```
- `activeProfileId` 를 그대로 PK로 써서 `existsByCustomer_CustomerIdAndArtwork_ArtworkId(customerId, artworkId)` 조회 → Member→Customer 재조회 불필요.

## 5. 결과 (트레이드오프)

- ✅ 접근 제어(문지기)와 뷰어 라벨링(공개 조회)을 애노테이션 하나로 표현, 컨트롤러가 깔끔.
- ✅ 겸용 계정도 "지금 접속한 role" 대로만 갈림.
- ⚠️ 리졸버가 주입한 엔티티는 detached → LAZY/쓰기 함정 → [[리졸버 주입 엔티티의 detached·LazyInit 함정]]
- ⚠️ SecurityContext credentials에 원본 JWT를 심는 구현에 의존(필터와 결합).

### 뷰어별 응답 (작품 상세조회 예 — 현재는 공개/작가 엔드포인트 분리, [[ADR-005 작품 조회 뷰어별 분기 전략]])
| 접속 | savedCount/viewCount | isSaved |
|---|---|---|
| 비로그인 | null | null |
| 고객 토큰 | null | true/false |
| 작가 토큰(본인, 작가 전용 엔드포인트) | 값 | — |

## 6. 등록 / 문서화

- `WebMvcConfig#addArgumentResolvers` 에 3개 리졸버 등록.
- `SwaggerConfig#addAnnotationsToIgnore(...)` 에 3개 애노테이션 등록 → springdoc이 `Artist`/`Customer`/`ViewerContext` 를 쿼리 파라미터로 펼치지 않게 함.

## 7. 관련 파일

- `global/auth/resolver/CurrentArtist(+ArgumentResolver)`, `CurrentCustomer(+ArgumentResolver)`, `CurrentViewer(+ArgumentResolver)`, `ViewerContext`
- `global/auth/resolver/CurrentProfileTokenSupport` (credentials에서 토큰 추출 공용)
- `global/auth/jwt/TokenProvider#getActiveRole/getActiveProfileId`
- `global/config/{WebMvcConfig, SwaggerConfig}`
