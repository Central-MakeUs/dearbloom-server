> **ADR-004 · Auth · Accepted · 2026-07-04 ~ 2026-07-12**
> 구글·애플 소셜 로그인을 네이티브(앱 WebView)와 웹(브라우저 리다이렉트) 양쪽에서 어떻게 처리할지 결정. → **네이티브는 SDK 토큰을 서버가 검증/교환, 웹은 리다이렉트. 커스텀 엔드포인트로 통합.**

## 맥락
- 클라이언트가 둘: **네이티브 앱(WebView 하이브리드)** 과 **웹 브라우저**.
- 네이티브는 소셜 SDK 로 이미 토큰을 받으므로 표준 리다이렉트 로그인과 흐름이 다르다.
- 애플/구글 각각 검증 방식이 다르고, Spring Security 의 oauth2Login 만으론 네이티브 토큰 흐름을 못 받는다.

## 결정
- **네이티브** `POST /api/auth/login` (단일): 앱이 넘긴 토큰을 서버가 검증/교환.
  - Google → `serverAuthCode`(offlineAccess) 를 서버가 구글에 교환.
  - Apple → `identityToken`(JWT) 을 **Apple JWKS 로 검증**(`NimbusJwtDecoder`) — **client_secret/.p8 불필요**.
- **웹** → 리다이렉트 방식(`/oauth2/{provider}/*`).
- **커스텀 엔드포인트** `/oauth2/{provider}/authorize|callback` 로 통일. (Spring Security 예약 매처 `/oauth2/authorization/*`, `/login/oauth2/code/*` 회피)
- 성공 시 accessToken/refreshToken 을 **HttpOnly 쿠키**로 설정. 로컬 웹(localhost)은 쿠키를 못 받으므로 **oneTimeCode 교환**(하이브리드) 별도.
- 유저 정보는 provider 무관 `SocialUserInfo` 로 통합, `AuthFacade` 단일 진입.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| Spring Security `oauth2Login` 만 사용 | 네이티브 SDK 토큰 흐름(서버 검증)을 수용 못 함 |
| Apple client_secret(.p8) 서명 방식 | JWKS 검증으로 충분, 키 관리 부담 제거 |
| provider별 컨트롤러 분리 | 진입점 산발 → 단일 컨트롤러/Facade 로 통합 |

## 결과 (트레이드오프)
- ✅ 네이티브·웹, 구글·애플을 일관된 회원 처리/쿠키 발급으로 통합.
- ✅ Apple 은 JWKS 검증이라 비밀키 관리 없음.
- ⚠️ Spring Security 매처와 충돌 피하려 커스텀 URL 사용 → 관례에서 벗어남(문서화 필요).
- ⚠️ 로컬 웹은 쿠키 제약으로 oneTimeCode 교환이라는 예외 경로 존재.

## 관련
- `domain/auth/controller/SocialLoginController`, `SocialLoginLocalWebController`, `domain/auth/facade/AuthFacade`
- `domain/auth/service/custom/{AppleNativeAuthService,GoogleNativeAuthService}`, `global/auth/oauth/custom/*`
- `domain/auth/dto/SocialUserInfo`
