> **ADR-020 · Domain · Accepted · 2026-08-13**
> 작품 탐색 목록의 필터(날짜·지역·인원)·정렬·무한스크롤을 어떻게 구현할지 결정. → **날짜 범위를 "요일 집합"으로 접어 EXISTS 하나로 처리하고, 지역·인원도 행이 복제되지 않게 EXISTS 로 건다. 페이지네이션은 offset 이 아니라 정렬 키를 담은 커서로 한다.**

## 맥락
- 화면은 **필터 4종(날짜 기간 / 지역 / 인원 / 정렬) + 무한스크롤**이다. 상단에 "전체 31" 같은 총 개수도 함께 보여준다.
- 작가 일정은 **규칙 기반**이라 날짜별 행이 없다([[ADR-008 작가 일정 관리 - 규칙 기반 가용성(sparse + 비트마스크)]]). "이 날짜에 가능한 작가"를 날짜로 직접 조회할 수 없다.
- 작가 활동지역은 `@ElementCollection`(`Artist.regions`) 이라 바깥에서 조인하면 **행이 복제**된다.
- 작품 가격은 패키지 최저가를 `Artwork.lowestPrice` 로 비정규화해 두었다.

## 결정
### 날짜 → 요일 집합으로 접기
요청이 **연속된 기간**이라 "기간 중 하루라도 가능"은 곧 **요일들의 OR** 이다. 7일 이상이면 7요일 전부가 되므로, 30일치 날짜를 IN 절에 늘어놓을 일이 없고 **최대 7개짜리 EXISTS 하나**로 끝난다.

- **예약 오픈 창(오늘~3개월)과 교집합을 먼저 잡는다.** 창 밖 날짜는 규칙과 무관하게 예약이 안 되기 때문. 교집합이 비면 빈 Set → 결과 0건, 날짜를 안 보냈으면 null → 필터 없음.
- **최대 30일**(`MAX_DATE_RANGE_DAYS`). 초과·역전·한쪽만 보냄은 400.
- **`WEEKLY_AVAILABLE` 규칙만 본다.** 특정 날짜가 `DATE_BLOCK`·예약 확정으로 통째로 막힌 경우는 걸러내지 않는다 — 구간 뺄셈이라 SQL 로 표현하기 어렵고, 기간 필터에선 오차가 사실상 없다.

### 지역·인원
- **지역** — `EXISTS` 서브쿼리 **안에서만** `regions` 를 조인한다. 바깥에서 조인하면 행이 복제돼 `distinct` 가 필요해지고, 그러면 `ORDER BY + LIMIT` 의 조기 종료가 깨진다.
- **인원** — `minHeadCount <= n AND (maxHeadCount IS NULL OR maxHeadCount >= n)`. `maxHeadCount = null` 은 "N인 이상"(상한 없음)이고, 화면의 "6인 이상"도 같은 식으로 처리된다.

### 커서 페이지네이션
- **커서 = 직전 페이지 마지막 행의 정렬 키**(`createdAt` / `lowestPrice` / `artworkId`). 정렬별로 쓰는 1차 키가 달라도 **세 값을 다 담는다** — 커서가 작아서 아낄 이유가 없고 정렬별 분기가 사라진다.
- **`artworkId` 를 항상 마지막 정렬 키로** 둔다. 1차 키가 같은 행의 순서가 흔들리면 커서 방식은 행을 **빠뜨리거나 중복**시킨다.
- **`size + 1` 개를 가져와 `hasNext` 판정** 후 잘라낸다. 별도 count 쿼리 없이 다음 페이지 유무를 안다.
- 커서는 **Base64(JSON)** 로 인코딩(`CursorCodec`)해 클라이언트가 내용을 해석하지 않게 한다.
- **커서 검증** — 형식만 맞고 값이 빈 커서(`"{}"`)를 그대로 쿼리에 넘기면 조건을 만들다 NPE 로 500 이 난다. `validateFor(sort)` 로 그 전에 400(`INVALID_CURSOR`).
- **총 개수는 별도 쿼리**. 페이지 조회와 **같은 `filterConditions()`** 를 쓴다 — 둘이 어긋나면 총 개수가 거짓말을 한다.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 날짜 범위를 날짜 IN 절로 | 30일이면 IN 에 날짜 30개. 규칙 기반이라 애초에 날짜 행이 없어 조인 대상도 없다 |
| 날짜별 가용 슬롯을 테이블로 미리 펼치기 | 작가 × 3개월 × 슬롯 = 폭발. [[ADR-008 작가 일정 관리 - 규칙 기반 가용성(sparse + 비트마스크)]] 에서 이미 기각한 방향 |
| `DATE_BLOCK`·예약까지 반영해 정확히 필터 | 구간 뺄셈이라 SQL 로 어렵다. 기간 필터에선 오차가 거의 없고, 상세 화면에서 어차피 재검증한다 |
| 지역을 바깥 조인 + `distinct` | 행 복제 → `distinct` → `ORDER BY + LIMIT` 조기 종료 무효화. 페이지 하나 뽑는 데 전체를 훑는다 |
| offset 페이지네이션 | 뒤 페이지일수록 느려지고, 스크롤 중 새 작품이 등록되면 **행이 밀려 중복·누락**된다 |
| 커서에 정렬별로 필요한 키만 담기 | 정렬마다 커서 형태가 달라져 디코딩 분기가 생긴다. 세 값 다 담아도 몇 바이트다 |
| 커서를 평문 id 로 | 가격순에서는 id 만으로 위치를 못 잡는다. 그리고 평문이면 클라이언트가 해석·조작하기 시작한다 |

## 결과 (트레이드오프)
- ✅ 날짜 필터가 **최대 7개 요일짜리 EXISTS 하나**로 끝난다. 기간이 길어져도 쿼리가 커지지 않는다.
- ✅ 행 복제가 없어 `ORDER BY + LIMIT` 조기 종료가 살아 있다.
- ✅ 스크롤 중 새 작품이 등록돼도 중복·누락이 없다.
- ✅ 필터 조건이 한 곳(`filterConditions`)이라 목록과 총 개수가 어긋나지 않는다.
- ⚠️ **날짜 필터가 낙관적이다.** 하루만 고른 경우 "그날 통으로 비워둔 작가"가 노출될 수 있다(요일 규칙은 맞지만 그날이 `DATE_BLOCK` 인 경우). 목록에서 걸러지지 않고 문의 시점에 슬롯 재검증으로 잡힌다([[ADR-009 스마트 문의·예약 - 상태 단일화와 슬롯 잠금]]).
- ⚠️ **총 개수는 매 페이지 재조회**된다. 필터가 EXISTS 2개라 데이터가 커지면 부담이 될 수 있다 — 첫 페이지에서만 세거나 근사치로 바꿀 여지.
- ⚠️ **Swagger 예시가 30일 규칙을 위반하고 있었다**(`startDate=2026-06-11`, `endDate=2026-10-18` = 129일). 그대로 Execute 하면 무조건 400 이라 "API 가 깨졌나" 오해를 만든다. 예시를 규칙 안으로 맞출 것.
- ⚠️ 30일 초과 시 나가는 에러가 `PARAMETER_BAD_REQUEST` 라 **어느 파라미터가 왜 틀렸는지 알 수 없다.** 날짜 범위 전용 코드나 메시지 보강이 필요하다.
