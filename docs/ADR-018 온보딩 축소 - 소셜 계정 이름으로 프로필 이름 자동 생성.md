> **ADR-018 · Domain · ~~Accepted(임시)~~ → Superseded · 2026-08-09 (2026-08-19 폐기)**
> 온보딩 단계를 줄이기 위해 이름·닉네임 입력을 뺄지 결정. → **요청에서 이름·닉네임을 받지 않고 소셜 로그인에서 확보한 `Member.name` 으로 자동 생성한다. 이메일이면 `@` 앞부분만 쓰고, 외자는 보정하고, 12자로 자른다. 되돌릴 것을 전제한 임시 정책이다.**
>
> ⛔️ **이 결정은 더 이상 유효하지 않다.** 2026-08-19 부로 자동 생성을 폐기하고 온보딩에서 이름·닉네임을 다시 입력받는다. 문서 하단 **갱신 (2026-08-19)** 절 참고. 본문은 당시 판단을 남기기 위해 그대로 둔다.

## 맥락
- 온보딩 이탈을 줄여야 한다. 고객은 실명·학교·지역, 작가는 닉네임·활동지역·대표이미지를 받고 있었다.
- Apple 심사에서 **"Sign in with Apple 이 이미 이름·이메일을 넘기는데 다시 입력받으면 안 된다"**(Guideline 5.1.1) 지적 소지가 있다. [[ADR-011 Apple 토큰 revoke - App Store 심사 대응(.p8 client_secret)]]
- 소셜 이름은 **형식이 제각각**이다. 특히 Apple 은 identity token 에 이름이 없어 `AppleNativeAuthService` 가 **이름 자리에 이메일을 넣어둔다.**
- 프로필 이름에는 검증 규칙이 있다 — 고객 실명 `[가-힣a-zA-Z]{2,12}`, 작가 닉네임 `[가-힣a-zA-Z0-9_]{2,12}`.

## 결정
- **요청 필드 제거** — `CustomerCreateRequest.name` / `ArtistCreateRequest.nickname` 주석 처리. DTO 에서 지우지 않고 주석으로 남겨 되돌리기 쉽게 한다.
- **`ProfileNameResolver` 로 `Member.name` 에서 생성.** 파사드가 아니라 `domain/member/util` 에 둔다 — 범용 문자열 유틸이 아니라 회원 도메인의 정책이라서.
- **보정 순서가 중요하다.**
    1. 값이 없으면 `noname`
    2. **이메일이면 `@` 앞(로컬 파트)만** — 길이부터 자르면 `abc123@priva` 같은 값이 남는다. 반드시 먼저
    3. 로컬 파트가 비면(`@example.com`) `noname`
    4. 외자면 뒤에 `아무개` — "김" → "김아무개"
    5. 12자 초과면 앞 12자
- **고객 실명 검증을 2~5자 → 2~12자로 확대.** 자동 생성 이름이 12자까지 나오는데 상한이 그보다 짧으면 **사용자가 자기 이름 때문에 프로필 수정을 저장하지 못한다.** 두 숫자는 항상 같이 움직여야 하므로 양쪽에 주석으로 묶어뒀다.
- **고객 프로필 이미지는 업로드받지 않는다** — 온보딩 때 `CustomerProfileImage` 4색 중 하나를 서버가 자동 배정. 작가만 대표 이미지를 올린다.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 이름 입력 유지 | 온보딩 단계가 줄지 않고 Apple 5.1.1 지적 소지가 남는다 |
| 소셜 이름을 화면에 **미리 채우고** 수정만 허용 | 정석이다. 다만 프론트 작업이 필요해 이번 범위 밖 — **되돌릴 때 갈 방향** |
| 자동 생성 없이 이름을 nullable 로 | 문의·채팅·리뷰가 전부 상대방 이름을 표시한다. 빈 값이면 화면이 깨진다 |
| 12자 자르기를 `@` 분리보다 먼저 | 이메일이 `abc123@priva` 처럼 잘려 남는다 |
| 외자를 `noname` 으로 | "김"은 실제 이름이다. 버리기보다 최소 길이만 맞추는 게 낫다 |
| 실명 상한을 5자로 유지하고 생성도 5자로 자름 | 소셜 이름 대부분이 잘려 의미를 잃는다 |
| 공백·숫자를 실명 패턴에 허용 | 검토했으나 반려 — 실명 필드의 의미가 흐려진다 |

## 결과 (트레이드오프)
- ✅ 온보딩에서 입력 필드 2개가 사라진다. Apple 5.1.1 소지도 줄어든다.
- ✅ Apple 로그인처럼 이름 자리에 이메일이 오는 경우에도 사람이 읽을 만한 값이 나온다.
- ✅ 생성 규칙과 검증 규칙의 상한이 맞아 자동 생성 이름이 프로필 수정에서 반려되지 않는다.
- ⚠️ **사용자가 자기 이름을 못 고른다.** 온보딩 직후 프로필 수정으로 가야 한다.
- ⚠️ **공백이 든 소셜 이름은 저장은 되지만 수정 API 를 통과 못 한다.** `"John Smith"` 가 그대로 들어가면 나중에 프로필을 못 고치는 상태가 된다 — 패턴에 안 맞는 이름을 `noname` 으로 떨구면 해결되지만 적용하지 않았다.
- ⚠️ 로컬 파트에 `.`·숫자가 섞이면(`000123.abc`) 같은 문제가 생긴다.
- ⚠️ 작가 닉네임이 자동 생성되면서 **금지어 검증(`NicknameValidator`)을 우회**한다. 소셜 이름이 "admin" 이면 그대로 들어간다.
- ⚠️ 임시 정책이라 **되돌릴 조건을 남긴다** — 프론트가 "미리 채우고 수정" UI 를 만들 수 있게 되면 주석 처리한 요청 필드를 되살리고 `ProfileNameResolver` 는 폴백으로만 둔다.

## 갱신 (2026-08-16) — 작가 닉네임만 규칙 완화

자동 생성된 이름이 검증을 통과해야 한다는 제약(위 "고객 실명 검증을 2~12자로 확대" 참고)과 같은 맥락에서, **작가 닉네임의 문자 규칙을 넓혔다.**

| | 이전 | 지금 |
|---|---|---|
| 작가 닉네임 | 한글·영문·숫자·`_` | **단어 사이 공백 허용** + `_` 허용 |
| 고객 실명 | 한글·영문 2~12자 | **그대로** |

### 왜 작가만 넓혔나
- 작가 닉네임은 **브랜드명**이다. `블루밍데이즈 스냅`, `시월 사진관` 처럼 공백이 들어가는 게 자연스럽다.
- 고객 이름은 **실명**이다. 예약·문의에서 신원 표시로 쓰이므로 공백·숫자를 허용하면 필드의 의미가 흐려진다.

### 남은 구멍
- 소셜 이름에 공백이 있으면(`"John Smith"`) 고객은 여전히 **저장은 되지만 프로필 수정을 통과 못 한다.** 자동 생성은 검증을 거치지 않기 때문. 위 "결과" 절에 적어둔 항목이 그대로 남아 있다.
- **작가 닉네임 자동 생성이 금지어 검증(`NicknameValidator`)을 우회**하는 문제도 그대로다. 소셜 이름이 `admin` 이면 그대로 들어간다.

두 구멍 모두 **패턴에 안 맞는 소셜 이름을 `noname` 으로 떨구는 것**으로 한 번에 막을 수 있다. 아직 적용하지 않았다.

## 갱신 (2026-08-19) — 자동 생성 폐기, 입력받는 방식으로 복귀

**상태: Accepted(임시) → Superseded.** 이 ADR 의 결정은 코드에서 완전히 사라졌다.

### 무슨 일이 있었나
| 날짜 | 커밋 | 실제 변경 |
|---|---|---|
| 2026-08-18 | `b3e9acb` "고객/작가 온보딩에 이름, 닉네임 요청으로 롤백" | 주석 처리했던 요청 필드를 되살림 |
| 2026-08-19 | `0899964`, `5f1871c` "온보딩 이름·닉네임 이메일 기반 자동 생성으로 변경 (임시)" | **`ProfileNameResolver` 와 그 테스트를 삭제** |

⚠️ **커밋 제목과 실제 diff 가 어긋나 있다.** 08-19 커밋 두 건은 제목상 "자동 생성으로 변경"인데 diff 는 resolver 삭제다. 히스토리만 읽으면 반대로 이해하게 되므로, **현재 상태의 근거는 이 문서가 갖는다.**

### 지금(HEAD) 실제 상태
- `CustomerCreateRequest.name` — `@NotBlank @ValidRealName`. **필수 입력**이다.
- `ArtistCreateRequest.nickname` — `@ValidNickname`. 받는다.
- `ProfileNameResolver` — **없다.** 이메일에서 이름을 뽑는 코드가 코드베이스 어디에도 남아 있지 않다.
- `ValidationPatterns.REAL_NAME` — `^[가-힣a-zA-Z]{2,5}$`. **2~12자 확대도 함께 되돌아갔다.**
- `ValidationPatterns.NICKNAME` — 2~12자, 단어 사이 공백 허용. **08-16 갱신분은 남아 있다** (자동 생성과 무관하게 브랜드명이라는 별개 근거가 있어서).

### 원래 적어둔 "되돌릴 조건"과의 차이
본문 마지막 ⚠️ 는 되돌릴 때 **"요청 필드를 되살리고 `ProfileNameResolver` 는 폴백으로만 둔다"** 고 적었다. 실제로는 **폴백조차 남기지 않고 삭제**했다. 그래서 지금은 소셜 이름을 이름 후보로 쓰는 경로가 아예 없다 — "미리 채우고 수정" UI 로 가려면 프론트가 소셜 이름을 직접 다뤄야 한다.

### 해소된 것 / 무효가 된 것
- ✅ 해소 — 사용자가 자기 이름을 직접 고른다.
- ✅ 해소 — 공백 든 소셜 이름이 저장은 되고 수정은 안 되던 상태. 이제 입력이 검증을 거친다.
- ✅ 해소 — 작가 닉네임이 금지어 검증(`NicknameValidator`)을 우회하던 문제.
- ✅ 해소 — 생성 상한과 검증 상한을 맞추려 실명을 12자로 늘려둔 부채. 5자로 돌아갔다.
- ❌ 무효 — "온보딩 입력 필드 2개가 사라진다". 다시 생겼고 **Apple 5.1.1 소지도 되살아났다.**
- ❌ 무효 — Apple 로그인처럼 이름 자리에 이메일이 오는 경우의 보정. 이제 사용자가 직접 입력하므로 필요가 없다.

### 미기록
**왜 되돌렸는지가 커밋 어디에도 없다.** 온보딩 이탈률이 문제가 아니었는지, 프론트가 "미리 채우고 수정" 을 못 하기로 했는지, 심사 쪽 판단이 달라졌는지 — 이 문서를 쓰는 시점에 근거를 찾을 수 없었다. 되돌린 사람이 한 줄 채워 넣을 것. **같은 논의가 다시 올라올 때 이 칸이 비어 있으면 처음부터 다시 하게 된다.**
